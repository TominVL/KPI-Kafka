 МЕТА РОБОТИ
Експериментально дослідити параметри продуктивності Kafka при обробці великих обсягів IoT-даних від енергетичних установок.
Параметри варіанту:
-  Кількість пристроїв: 12 енергоблоків ТЕС (вугілля, газ, змішане паливо)
-  Частота передачі даних: кожні 10 секунд
-  Географія: Східна Україна (48.0–50.0°N, 36.0–40.0°E)
-  Особливості: контроль викидів, оптимізація спалювання, регулювання навантаження
 ТЕСТОВЕ СЕРЕДОВИЩЕ
 Конфігурація
-	Система: Windows 10 Pro
-	Java: 17
-	Kafka: 3.7.1
-	Python: 3.11
-	Hardware: 4 cores, 16 GB RAM, SSD
-	Архітектура Kafka: Single-broker
-	Zookeeper: 3.9.2
 Тестові дані
-  Цільова пропускна здатність: 800 записів/сек
-  Тип даних: телеметрія теплових енергоблоків
-  Фокус: моніторинг fuel_flow, steam_pressure, emissions
-  Кількість записів: 1200 згенерованих JSON повідомлень
-  Розмір повідомлення: 256 байт

Оптимальна кількість: 8 партицій для аналітики за fuel_type (coal/gas/mixed).
Real-time (онлайн моніторинг fuel_flow / steam_pressure, алерти кожні 10 с):
•	batch.size=16KB, linger.ms=0, compression=none, partitions=8
•	Латентність: <1 ms (avg ~0.10 ms, p99=1 ms) | Throughput: ≈800 rec/sec
•	Використання: критичні алерти environmental monitoring (миттєва реакція на відхилення тиску/витрати палива)
Batch обробка (оперативна аналітика/дашборди, економія трафіку):
•	batch.size=64KB, linger.ms=10–20, compression=lz4, partitions=8
•	Compression: ~55–65% економії | Throughput: >800 rec/sec 
•	Використання: щохвилинні/щогодинні агрегати для fuel efficiency і compliance, прийнятна затримка з помітною економією місця
Архівування (історія для звітності та аудитів):
•	batch.size=256KB, linger.ms=50, compression=zstd, partitions=12
•	Compression: ~65–75% економії | Storage optimization: ≈3× зменшення обсягу (ефективно для довгострокового зберігання)
•	Використання: довготермінові логи fuel_flow/steam_pressure для environmental reporting (latency не критична)

Головний trade-off для системи моніторингу ТЕС:
•	Latency vs Compression/Storage.
o	Малий batch + linger=0 + compression=none → мінімальна затримка (avg ~0.07–0.10 ms, p99≈1 ms при 800 rec/s), але без економії місця.
o	Великий batch + linger=50 + compression=zstd → макс. економія сховища (~70%), але затримка зростає.
Критичний параметр:
•	Для реагування на екологічні відхилення (steam_pressure, fuel_flow) пріоритет — latency (першочергово p99/p99.9), а не стискання.
Рекомендована стратегія:
1.	Real-time шар: batch.size=64KB, linger.ms=0, compression=none або lz4, partitions=8, ключ = fuel_type. Дає низькі хвости і стабільні ~800 rec/s.
2.	Near-real-time/Batch шар: batch.size=64KB, linger.ms=10–20, compression=lz4 
- баланс пропускної та економії (~60%).
3.	Архівний шар: batch.size=256KB, linger.ms=50, compression=zstd, partitions=12 — мінімум місця для історії/звітів.

ВИСНОВКИ
Досягнення цілей:
-	Досліджено вплив batch.size/linger.ms: менші batch і linger=0 дають мінімальну затримку; великі batch + великий linger різко збільшують p95/p99, придатні лише для пакетів/архіву.
-	Порівняно compression алгоритми: none — найменша latency; lz4 — найкращий баланс швидкість/економія (~55–65%); zstd — максимальне стиснення (~65–75%), але більші хвости.
-	Проаналізовано масштабованість: за таргетом 2000 rec/s один продюсер упирається у ліміт, тому приросту від 4→8→12 партицій не видно; для демонстрації скейлінгу потрібні вищий таргет або кілька продюсерів.
-	Розроблено рекомендації для системи моніторингу ТЕС: реальний час — 64KB/0ms (none/lz4), аналітика — 64KB/10–20ms (lz4), архів — 256KB/50ms (zstd), партиціонування за fuel_type.
Ключовий результат:
Оптимальна конфігурація для системи моніторингу ТЕС (real-time alarms):
64KB + 0ms + lz4/none + 8 партицій = ≈800 rec/sec при ~0.07–0.10 ms avg (p99 ≈ 1 ms).
Специфіка енергетичних даних: fuel_flow і steam_pressure мають передбачувані патерни та помірну ентропію (добре стискаються lz4/zstd); fuel_type — категоріальний ключ, який забезпечує локальність і рівномірний розподіл навантаження по партиціях; 12 пристроїв із періодом 10 с формують стабільний рівномірний потік.
Практичне значення:
Результати можуть використовуватись для:
1.	Оперативних екологічних алертів (перевищення тиску/витрати палива) з мінімальною затримкою.
2.	Дашбордів ефективності спалювання та короткострокової аналітики з помірним стисненням (lz4).
3.	Довготермінового зберігання й звітності (zstd, великі batch) з економією сховища ~3×.
